**JWT（JSON Web Token）** 是一种开放标准（RFC 7519），用于在网络上作为 **JSON** 对象在客户端与服务器之间传输数据。JWT 通常用于身份验证和授权，也可以用于信息的安全传递。它的主要优势在于能够在无状态（stateless）的情况下，进行跨平台的身份验证和数据传递。

### 1. **JWT 的结构**

一个 **JWT** 由三部分组成，分别通过点（`.`）分隔：

```
header.payload.signature
```

#### 1.1 **Header（头部）**

**Header** 通常包含两部分：**Token 类型** 和 **签名算法**。

- `alg`：签名算法，比如 HMAC SHA256 (`HS256`) 或 RSA (`RS256`)。
- `typ`：Token 类型，通常是 "JWT"。

**示例**：

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

这个部分会被进行 **Base64URL** 编码。

#### 1.2 **Payload（载荷）**

**Payload** 是 JWT 的主体部分，包含需要传递的数据。JWT 的 Payload 通常包含几种类型的声明（claims）：

- **注册声明（Registered Claims）**：标准化的一些声明字段，定义了关于 JWT 的预定义字段，如 `iss`（发行人）、`exp`（过期时间）、`sub`（主题）和 `aud`（受众）等。这些字段是可选的。
- **公共声明（Public Claims）**：用户自定义的声明，可以是应用中的数据。比如用户 ID、角色等。
- **私有声明（Private Claims）**：应用和服务之间共享的自定义声明，防止冲突。

**示例**：

```json
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "exp": 1719095999
}
```

**Payload** 也会经过 **Base64URL** 编码。

#### 1.3 **Signature（签名）**

**Signature** 是确保 JWT 的数据完整性的一部分，用来防止数据篡改。签名由以下三部分构成：

```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```

签名的目的是验证发送者是可信的，并确保 Token 在传输过程中未被篡改。

- 对 **Header** 和 **Payload** 分别进行 **Base64URL** 编码。
- 使用签名算法（如 `HS256`）和服务器上保存的密钥（`secret`）进行签名。
- 生成的签名也会被添加到 Token 中。

### 2. **JWT 的工作流程**

JWT 主要用于身份认证，典型的使用场景是用户登录。流程如下：

#### 2.1 用户登录

1. 用户通过客户端发送用户名和密码登录。
2. 服务器验证用户的身份，如果验证通过，服务器生成一个 **JWT**，该 Token 包含用户的身份信息（如用户 ID、角色）等，并将 **JWT** 返回给客户端。

#### 2.2 客户端保存 Token

客户端（通常是浏览器或移动应用）收到 **JWT** 后，会将其存储在本地存储、Session Storage 或 Cookie 中。注意，这部分操作是客户端完成的，服务器不需要存储 Token。

#### 2.3 后续请求

1. 客户端在后续的请求中，将 **JWT** 附加在请求头的 `Authorization` 字段中，格式如下：

   ```
   Authorization: Bearer <token>
   ```

2. 服务器收到请求后，通过检查 Token 的有效性（通常是解码并验证签名）来判断用户是否具有访问权限。

#### 2.4 服务器验证 Token

1. 服务器使用事先设定的密钥对 **JWT** 进行解码和验证签名。
2. 验证通过后，服务器允许用户访问受保护的资源。
3. 如果 **JWT** 失效或被篡改，服务器会拒绝该请求。

### 3. **JWT 的优缺点**

#### 3.1 优点

- **无状态（Stateless）**：JWT 是无状态的，服务器无需保存任何会话数据。所有信息都存储在 Token 中，这使得 JWT 非常适合分布式系统和微服务架构。
- **易于扩展**：JWT 可以携带大量数据，并且格式化为 **JSON**，非常适合跨平台和跨语言的应用。
- **安全性**：通过签名机制，服务器可以确认数据没有被篡改。
- **减少数据库查询**：由于 Token 中包含了用户的身份信息，服务器可以不再频繁地查询数据库。

#### 3.2 缺点

- **Token 无法撤销**：一旦 JWT 被签发，除非设置过期时间，否则在其有效期内，Token 是不可撤销的。这意味着如果 Token 被泄露，攻击者可以在过期之前一直使用它。
- **Token 过长**：由于 JWT 包含用户信息，并且需要经过 Base64 编码，Token 可能会较长，增加请求大小。
- **易受攻击**：如果密钥管理不当或加密算法使用不安全，JWT 可能容易遭受攻击，如字典攻击或中间人攻击。

### 4. **JWT 与会话管理的对比**

- **传统会话管理**：服务器通过会话 ID 来标识用户，并在服务器端维护会话状态。每次请求，用户的会话 ID 会通过 Cookie 发送到服务器，服务器根据会话 ID 查找对应的用户会话数据。

  **问题**：对于分布式架构，服务器需要共享或集中管理会话数据（如 Redis），增加了复杂性。

- **JWT 认证**：JWT 是无状态的，服务器不需要存储会话数据。用户身份信息保存在 Token 中，每次请求时，客户端将 Token 发给服务器，服务器通过解析和验证 Token 来获取用户信息。

  **优势**：适合分布式系统，减少服务器的存储压力。

### 5. **JWT 的常见用途**

#### 5.1 身份认证

JWT 最常见的用途是作为身份验证机制。在用户登录后，服务器生成一个 Token，客户端保存该 Token 并在后续请求中携带它。服务器通过验证 Token 来识别用户身份。

#### 5.2 授权

JWT 还可以用于授权。Token 中包含了用户的权限信息，服务器可以通过解析 Token 来判断用户是否有权限访问特定资源或执行某个操作。

#### 5.3 信息交换

由于 **JWT** 是签名的，可以确保数据的完整性，因此它可以用于安全地在各方之间传递信息。比如，两个服务之间可以使用 JWT 作为信息交换的媒介，确保信息在传输过程中未被篡改。

### 6. **JWT 的安全性问题与防护措施**

尽管 JWT 提供了便利，但在使用时需要注意一些安全问题。

#### 6.1 **Token 签名的安全性**

签名算法的选择和密钥的安全性是保护 JWT 的关键。如果使用的签名算法过于简单（如 HS256）或者密钥泄露，攻击者可以伪造 Token。因此，推荐使用强加密算法（如 RSA、ES256）和安全的密钥管理机制。

#### 6.2 **Token 存储的安全性**

客户端如何存储 JWT 是一个安全问题。如果将 Token 存储在不安全的位置（如浏览器的 LocalStorage），可能会被 XSS 攻击窃取。因此，一般推荐将 Token 存储在 **HttpOnly Cookie** 中，减少被脚本获取的风险。

#### 6.3 **Token 的过期处理**

JWT 由于是无状态的，服务器不会保存其状态，因此无法直接撤销 JWT。因此，建议在生成 Token 时设置合理的 **过期时间（exp）**，并结合 **Refresh Token** 机制，确保 Token 在短时间内失效，并避免长时间有效的 Token 被滥用。

#### 6.4 **防止重放攻击**

重放攻击是指攻击者窃取用户的 Token 后，重复使用它来伪造请求。可以通过以下方式减少风险：

- 在 Token 中引入唯一标识符（`jti`）来标识 Token 并在服务端记录它的使用情况。
- 限制 Token 的有效期，缩短攻击者的可用时间。
- 使用 **OAuth 2.0** 标准中的 Refresh Token 来定期刷新用户的访问 Token。

### 7. **JWT 与 OAuth 2.0**

JWT 常被用于 **OAuth 2.0** 认证框架中。OAuth 2.0 是一个开放标准授权协议，JWT 则作为 OAuth 2.0 的访问令牌，帮助服务端验证请求的合法性。
